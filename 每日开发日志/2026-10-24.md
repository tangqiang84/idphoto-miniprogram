## 三、问题与解决

1. **`SignatureFailure` 是误导性文案** → 真正原因是 "exceeding request size limit"（超过 1MB）。
   腾讯云 OpenAPI **旧签名**方式 body 上限 1MB，超限在**网关层**拒绝，请求没到云函数 → 改代码无意义。
2. **`SAFETY=0.96` 是被自己踩出来的**：第一版按 900KB 反算像素仍未通过——`downsampleRGBA` 会把目标像素数
   **向上取整到整数宽高**（172762 → 360×480 = 172800），正好顶穿。取整是隐式的像素膨胀源。
3. **区分两种限制**：控制台「云端测试」1MB（旧签名） vs 运行时 `callFunction` 5MB。云端测试跑不通 ≠ 线上跑不通。

## 八、【11:0x】#53 口径修正：控制台阈值不是 1MB，实测远更低

**新证据（owner 实测回传）**：
- `cloudfn-payload-small.json`（150×200 / **156KB**）→ ✅ 验证成功
- `cloudfn-payload.json`（353×470 / **864KB**）→ ❌ 同样的 `AuthFailure.SignatureFailure ... exceeding request size limit`

**结论修正**：我上一轮按**官方文档**口径设的 900KB 预算是错的。
腾讯云文档写「POST 使用签名方法 v1 时不得超过 1MB、v3 支持 10MB」，
但**云开发控制台插件（cloudconsolev1）实测更严**——真实阈值落在 (156KB, 864KB) 之间。
官方文档给的是**通用 API 上限**，不能当成控制台的上限用。

**改动**：
- `make_cloudfn_payload.js`：预算改为 `Number(process.env.CONSOLE_LIMIT_KB || 128) * 1024`（默认 128KB，实证安全区），
  保留 `SAFETY=0.96` 与落盘前出口断言；新增环境变量覆盖便于自行试探上限。
- 产物三档：`cloudfn-payload.json` **123KB**（默认，已进剪贴板）/ `cloudfn-payload-small.json` 156KB（已实证 ✅）
  / `cloudfn-payload-probe512.json` **492KB**（探针，供愿者二分定位真实阈值）。
- 三份载荷本地 #50 自洽校验全过（RGBA 字节 === w×h×4，`handleMatting` 无错）。
- 文档同步：手册 3q、避坑指南报错速查索引（把「1MB」改成实测口径）、台账 #53（补记一次口径修正）、任务台账 #34。

**方法结论**：控制台只用来验「路由是否通、是否出图」；**抠图质量验证改走小程序端 `callFunction`（5MB 运行时上限）
或本地 `baidu_live.js`（全分辨率直连百度）**，不要在控制台上追求大图——这条路本来就走不通。

**经验沉淀（本次最值钱的一条）**：
- **文档口径 ≠ 实际口径**。官方「1MB」是通用 API 上限，控制台插件在其之上又加了一层。
  我的错误不是没查文档，而是**把文档值直接当成了产品实际值**——中间隔着一个"插件"。
- **修问题时要留一个"我可能错"的出口**：上一轮我把 900KB 写成"实测通过"，其实只跑了脚本自断言，没真去控制台粘一次。
  **本地断言通过 ≠ 线上可用**，凡涉及外部系统的阈值，必须有一次真实验证回来才能结案。

## 十、【11:4x】#54：推翻「960×1280 无需降采样」——真正生效的是像素封顶不是体积

**触发**：owner 贴出 `baidu_live.js` 的真实输出，其中
`上传像素 261813（是否降采样：true），urlencode 后 body 549676 字节`。
这与我之前写进 MEMORY 的「960×1280 ≈1.89MB < 4MB，**无需降采样**」直接冲突。

**查证（以磁盘现状为准）**：`cloudfunctions/matting/baiduSeg.js:42`
```js
const DEFAULT_MAX_PIXELS = 512 * 512;          // = 262144  ← 真正生效的约束
const DEFAULT_MAX_BODY  = floor(4MB * 0.95);  // = 3.81MB  ← 几乎永不触发
```
960×1280（1,228,800 px）> 262,144 → 降到 261,813 px（443×591）上传 → body 仅 537KB。
**4MB 的 body 上限从来不是瓶颈。**

**我的错误性质**：把**体积估算当成了生效约束**。估算本身没错（1.89MB 确实 < 4MB），
错在没回头看代码里到底先判哪个条件——`if (w*h > maxPixels)` 在编码之前就执行了。

**影响**：百度回的 scoremap 是 443×591，再双线性放大回 960×1280 → 发丝边缘细节约为原图的 1/2.2 分辨率。
实测质量仍优秀（person_num=1、前景占比 39.4%、半透明边缘 0.6%、647ms），所以**不是 bug，是未调优**。

**待决策（不改，先摆证据）**：把 `DEFAULT_MAX_PIXELS` 提到 1024×1024 或 1280×1280。
安全性由现成的两层兜底：① 编码后实测 body，超限按 ×0.7 收缩（最多 8 次）② 4MB 硬上限。
代价：上传体积 ~1.9MB、耗时上升（百度侧与云函数编解码）。改前需 A/B 实跑对比质量与耗时。

**新增 #54 台账条目**；MEMORY.md 旧结论已划掉并注明推翻（不删除，保留纠错痕迹）。

**经验沉淀**：
- **「理论上够用」不等于「实际会走那条路」**：判断约束必须看代码里的**判定顺序**，不是看数值关系。
- 估算型结论（体积够不够）和代码型结论（会走哪个分支）是两类东西，前者不能替代后者。
- 用户随手贴的终端输出里藏着能推翻结论的字段（这里是 `downscaled: true`）——**贴什么都要读一遍**。
