## 经验沉淀

- **报错里的动词比名词重要**：`exceeding request size limit` 才是根因，`SignatureFailure` 只是被顺带触发的文案。
- 区分**控制台限制**（1MB）与**运行时限制**（`callFunction` 5MB）；云端测试跑不通 ≠ 线上跑不通。
- 生成类工具的**默认值必须先自跑一遍**——坏默认值会让使用者误判成环境问题，排查成本极高。

## 2026-10-24 11:0x #53 口径修正：控制台阈值不按文档走
- owner 实测：156KB ✅ 通过 / 864KB ❌ 同样报 exceeding request size limit。
  我上一轮按官方文档「旧签名 ≤1MB」设的 900KB 预算是错的——**文档是通用 API 口径，云开发控制台插件实测更严**，
  真实阈值在 (156KB, 864KB) 之间。
- 改动：脚本预算改 `CONSOLE_LIMIT_KB`（默认 128，实证安全区）；产物三档
  123KB（默认，已进剪贴板）/ 156KB（已实证 ✅）/ 492KB（探针，供二分）。三份 #50 自洽校验全过。
- **方法结论**：控制台只验路由；抠图质量走小程序端 callFunction(5MB) 或本地 baidu_live.js(全分辨率)。
- **教训**：文档口径 ≠ 产品实际口径（中间隔着"插件"那层）；本地断言通过 ≠ 线上可用，
  涉及外部系统的阈值必须有真实验证回执才能结案。

## 2026-10-24 11:4x #54：推翻「960×1280 无需降采样」
- 证据：owner 贴的 baidu_live 输出 `上传像素 261813（downscaled: true），body 549676 字节`。
- 根因：`baiduSeg.js:42 DEFAULT_MAX_PIXELS = 512*512 = 262144` 才是生效约束；4MB body 上限几乎永不触发。
  960×1280 → 降到 443×591 上传（body 仅 537KB），alpha 再双线性放大回原尺寸（边缘细节约 1/2.2）。
- 我的错误：**把体积估算当成了生效约束**——没看代码里的判定顺序（像素封顶在编码之前）。
- 影响：不是 bug 是未调优（实测质量优秀：person_num=1/前景 39.4%/边缘 0.6%/647ms）。
- 待决策：封顶提到 1024×1024 或 1280×1280（体积由 4MB 兜底 + 超限 ×0.7 收缩），改前 A/B 实跑。
