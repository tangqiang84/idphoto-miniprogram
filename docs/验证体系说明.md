## 三、业务断言库：每条断言怎么判、局限在哪

`工具链/assert_business.js`（纯 Node，不依赖 IDE）。每条返回 `{ok, actual, expected, detail}`，
可单独 CLI 跑（`--assert <名称>`），也可 `--selftest` 自测（当前 **24 条用例全绿**）。

### 3.1 `assertPixelSize(file, specId, dpi)`
- **判定**：读成品像素尺寸，与 `core/specLibrary.js` 的 `getPixelSize(specId, dpi)` 比对，容差 ±2px（取自 `core/compliance.js` 的 `DIM_TOL`）。
- **额外能力**：`opts.expectedWidth/Height` 支持「非规格路径」（如 T2 未选规格 → 保持原图尺寸），此时按原图长边≤800 等比缩放推算期望值。
- **局限**：不校验 DPI 元数据（官方报名系统本就不校验）。

### 3.2 `assertBackgroundColor(file, expectedHex, tolerance=12)`
- **判定**：取四角内移共 **12 个采样点**的**众数色**（8 级/通道量化后投票），与期望色比**逐通道最大差**（Chebyshev）。
- **为什么用众数而非单点**：中心与四边中点必然落在人脸上；单点采样会被压缩噪点、发丝、肩线带偏。众数 + 四角多点是抗单点污染的最简做法。
- **透明底**：`expectedHex='transparent'` 时判「四角 alpha<250 的占比 ≥75%」；反之若期望纯色而成品是透明底，明确判失败并说明。
- **实测**：真实成品实测众数色与目标色偏差 1~4（JPEG 压缩噪声），支撑率 75%~100%。

### 3.3 `assertHeadRatio(file, specId, tolerance=0)` ★ 最容易糊弄的一条
三级判定，**每一级都标注可信度**：

| 级别 | 依据 | 可信度 |
|---|---|---|
| 1 关键点实测 | 传入 `landmarks` → `core/face.js` 的 `headMetricsFromLandmarks` + `ratioWithinWindow` | 实测（但「头顶」本身仍是脸长÷0.74 外推） |
| 2 像素估算 | 从成品像素反推：**前景掩膜 → 行宽曲线 → 头顶行（发际线以上的起始行）→ 颈部最窄行（下巴）** → 头长÷图高 | **估算**，误差约 ±5~8 个百分点 |
| 3 无法判定 | 既无关键点、成品也非纯色底 | `ok=false` + 明说「无法测量」，**不猜、不用固定值冒充** |

- **为什么不用 `core/face.js` 的 `headMetricsFromBBox`（0.30×人像框高）**：
  该系数假定人像全身在画面内。**成品是按头占比裁切后的图**，人物从头顶延伸到画面下沿，
  人像框高≈图高 → 0.30×图高 ≈ 0.30，与规格要求的 61%~71% 差约 36 个百分点，**会把合格成品判成严重不符**。
  故成品口径改用颈部轮廓法（方法见上）。`opts.method='bbox'` 仍可强制使用 core 口径（测**源图**时用）。
- **实测标定**：用几何已知的合成证件照（真实头占比 66.1%）验证，估算值 63.7%，**误差 2.4 个百分点**。
- **环境限制（重要）**：开发者工具模拟器**不支持人脸检测**（`services/faceService.ts` 明确跳过 `devtools` 平台）
  → 裁切降级为「按画面居中裁剪」→ 头占比必然不落规格区间。
  `batch_real.js` 会读页面「智能裁切」文案识别这一状态，把该断言标注为 **envLimited（环境限制）**并从业务失败中剔除，
  **同时明确标注「真机才可验」** —— 不把环境问题粉饰成产品通过。

### 3.4 `assertFileSize(file, maxKb, {advisory})`
- **判定**：`fs.statSync().size / 1024` 与上限比对。
- **600dpi 档**：按产品口径（`core/compliance.js` 的 `level='advisory'`）→ `advisory=true` 时 `ok` 恒为 true，
  但 `severity='advisory'` 且 detail 写明超出量 —— **提示不阻断**，与产品行为一致。

### 3.5 `assertNoWatermark(file)` ★ 另一条容易糊弄的一条
**两条独立证据，取「或」**：

- **证据 A（确定性，零误报）**：扫描 PNG 的 `tEXt/iTXt/zTXt` 块、JPEG 的 `COM/APPn` 段，
  命中水印关键词（watermark / 水印 / 仅供 / 样张 / sample / preview / demo…）→ 直接判失败。
  只能抓「把水印信息写进文件」的粗心实现。
- **证据 B（像素启发式）**：文字水印 = 一行**互不相连的笔画**。因汉字/字母由 5~6 块笔画组成，
  故不用「块=字形」模型（那样建模会**漏报**），而用**子行模型**：
  1. 子行 = **底边（基线）对齐**的一组连通块（笔画高度可不同：`S` 的横笔 2px、竖笔 14px，但坐在同一基线）；
  2. 候选子行须同时满足：≥3 块 + 同一颜色 + **笔画细长**（min(宽,高) ≤ 0.34×行高，排版学性质）
     + **悬浮于平坦背景**（整行外扩 **5% 图高**的环带中底色占比 ≥88%）
     + 整行宽度 ≥ 3×行高 + 行高 ≥ 4px（1~2px 的行是 JPEG 压缩噪点）；
  3. **一次性判据**：候选子行 ≥3 条 → 判为**重复纹理**（格纹/花纹在多处重复），整图不报水印。

**实测标定（这是关键的诚实性证据）**：
- **正样本**：用内置 5×7 点阵字体渲染一行 `"SAMPLE"` → **能检出**（防止「永不报警」的假安全）；
- **负样本**：`素材/测试截图/acceptance{,_suit}/` 共 **22 张真实成品 → 0 误报**。

**局限（必须读）**：
- 半透明水印（与底色色差 <42）会漏检；
- 压在**人像身上**（而非平坦背景上）的水印会被「悬浮背景」约束漏掉；
- 与人像主体**相连**的水印会被「主体排除」漏掉；
- 单个字/单笔的水印不会被检出（需要 ≥3 块成行）；
- **斜向平铺**的水印（行位置不固定）可能漏检；
- 原图自带且恰好满足全部约束的装饰图案仍可能误报。
→ 结论应读作「**未检出明显文字水印**」，AC7 的最终确认仍需人眼过图。

### 3.6 `assertSuitNotCoverFace(beforePath, afterPath, faceRect)` + `assertSuitKeepsFacePixels` + `assertSuitDoesNotCoverFace`
PRD D2/AC6「换装不得改动五官」。**三条互补**：

| 函数 | 需要的输入 | 判定依据 |
|---|---|---|
| `assertSuitNotCoverFace` | 换装前图 + 换装后图 | 脸部框内逐像素差：显著变化像素占比 <2% 且平均通道差 <6（显著变化 = 任一通道差 >24）。**优先复用 `core/suitDiff.js` 的 `compareFaceRegion`**（owner 2026-10-28 并行新增），使断言与产品共用同一套口径；该文件不存在时回退本文件内的独立实现 |
| `assertSuitKeepsFacePixels` | 换装前图（参考）+ 换装后图 | **肤色保持率**：参考图脸部框内「是肤色」的像素，换装后**不再是肤色**的比例 ≤8% |
| `assertSuitDoesNotCoverFace` | 仅换装后图 | 肤色区末端**收窄比**（末端行宽÷该区最大行宽）>0.5 → 判为脸被**横切**；或脸部框内西装像素占比 >12% |

- **`assertSuitKeepsFacePixels` 是最可靠的一条**（实测 11 张真实成品：**9/9 检出、0 假阳**）。
  原理：T1（不换装）与 T3（换装）走**同一条共享管线**（`services/pipeline.ts`）、同一规格 dpi → **裁剪几何一致、两图逐像素对齐**；
  于是「参考图是肤色、换装图不是肤色」只对**脸部被覆盖**敏感，归因干净（纯像素差会被底色变化与重压缩噪声污染）。
- **为什么不用「西装起始行 < 肤色结束行」**：肤色区包含脖子/前胸皮肤，领口落在脖子处时该条件天然成立 → 实测把正常的 3652.jpg 误判为假阳，已剔除。
- **局限**：依赖两图**几何对齐**；肤色规则对暖光/滤镜/非东亚肤色可能失效；单图版实测检出 7/9（2 张漏检），**有参考图时一律用 `assertSuitKeepsFacePixels`**。
- **说明**：`core/suitDiff.js` 由 owner 于 2026-10-28 并行新增（本次开发期间出现），
  故 `assertSuitNotCoverFace` 已改为**优先复用**它（口径与产品一致）；
  `assertSuitKeepsFacePixels` / `assertSuitDoesNotCoverFace` 是本任务新增的补充口径，仍为独立实现。
  全程**未修改 `core/` 任何文件**。

### 3.7 `assertFaceRegionClean(file, faceRect)`
- **判定**：脸部框内灰度统计量 —— ①**纯色**：标准差 <3 → 判为抠图/合成失败；②**花屏**：相邻像素梯度均值 >26 **且** 高频像素占比 >50% → 判为噪点/花屏。
  依据：真实脸部既有平滑皮肤（梯度低）也有五官边缘（梯度高），整体梯度居中段；纯色图梯度≈0；花屏图梯度几乎处处接近满量程。
- **局限**：大特写（梯度本就高）可能误判为花屏 → 判 FAIL 时 detail 会给出实际统计量供人工复核。

## 四、批量业务验收（`工具链/batch_real.js`）

- **输入**：`素材/真实头像/` 全部 11 张（含负例）× T1/T2/T3；默认用真实素材，**不用合成图**。
- **复用既有套路**（不重写）：IDE 连接用 `工具链/automator_connect.js` 的 `connectAutomator`；
  页面跳转沿用 `batch_acceptance.js` 的「点首页卡片」；图片注入沿用「写 USER_DATA_PATH + mock chooseImage」；
  状态等待用 `工具链/smoke_kit.js` 的 `waitForStatus`（只认 `.status-line`）。
- **成品落盘**：`素材/测试截图/real_batch/run-<YYYYMMDD-HHMMSS>/<素材名>/<工具>/` → `original.<ext>`（原图副本）+ `result.jpg`（成品）+ `page.png`（页面截图）+ `assertions.json`（断言结果）；汇总 `.../run-<时间戳>/results.json`。
  - **每次跑批写入新的时间戳目录，永不删除、永不覆盖旧结果**（全局规则 F-7：禁止先删后跑）。重跑直接跑即可，旧结果原地保留。
  - 目录指针见 `素材/测试截图/real_batch/LATEST.txt`；`--latest`（或 `--no-ide`）自动复用最近一次跑批目录，复用时旧 `results.json` 会先备份为 `results.backup-<时间戳>.json`。
  - `--out <目录>` 显式指定输出目录（原样使用，不追加时间戳）。
- **两个数字严格分开**（PRD 15.4 禁止项①）：
  - **连通性通过** = 链路跑完且拿到成品；
  - **业务断言通过** = 上述业务断言全绿。
  两者**不合并成一个「通过」**。
- **三类非失败状态**（避免把环境/口径问题粉饰成产品缺陷）：
  - `envLimited`：环境限制导致（如模拟器无人脸检测 → 头占比断言）→ 从业务失败中剔除，但注明「真机才可验」；
  - `notApplicable`：该路径下断言不适用（如 T2 未选规格时的头占比）；
  - IDE 通道连不上（`timeout waiting for automator response`，问题台账 #86/#87）→ 自动 `cli auto` 开通道重试，
    **打印重试次数**，连不上则报「环境不可用 + 如何开通道」，**不判定脚本失败**。
- **按工具区分规格口径**（否则会误判）：T1/T3 默认选一寸 → 按规格像素断言；T2 默认**不选规格**（保持原图尺寸）→ 按原图长边≤800 缩放推算断言。

#### 实跑中踩到的环境坑（已写进脚本的诊断输出）
1. **`dist/` 被清空 → IDE 页面栈永远起不来**。表现为 automator 报
   「timeout waiting for automator response」，但**通道本身是连上的**（`connect` 成功）。
   真因是开发者工具没有可加载的编译产物。`batch_real.js` 现在会先检查 `dist/app.json` 是否存在，
   缺失时直接给出「先编译」的提示，而不是笼统说「通道连不上」。
2. **通道陈旧**（问题台账 #86/#87）：`cli auto --auto-port <port> --port 16780` 重新开通道后即可用；
   脚本已内置「cli auto → 重试 connect → 打印重试次数」的自愈流程。
3. **connect 成功 ≠ 页面栈就绪**：连接建立后 IDE 侧 webview 可能还没起来，
   此时立刻调 `currentPage()` 会抛「Cannot destructure property 'rawPath' … as it is null」。
   故 `batch_real.js` 增加 `waitForAppReady()` 轮询等待（12 次 × 2s）。
4. **`$$` 是 Page 上的方法**，不是 miniProgram 上的（`mp.$$ is not a function`）。

## 四之二、本次实跑发现的真实业务缺陷（重要）

> 实跑口径：11 张真实素材 × T1/T2/T3 = **33 个组合**，一次跑完（2026-10-28 20:04）。
> 结果：**连通性 33/33 通过**；**业务断言 24/33 通过**，9 个失败**全部集中在 T3 换装盖脸**。
> T1（22 个组合）与 T2（11 个组合）业务断言**全绿**。


**T3 换装把西装领口盖到了脸上 —— 11 张真实素材里 9 张中招。**

这不是新引入的缺陷，而是**既有缺陷此前被连通性验收掩盖了**：
旧的 `batch_acceptance.js` 对同一批素材只记录状态行「换装完成」→ 判定为通过；
本批业务验收用 `assertSuitKeepsFacePixels`（肤色保持率口径）逐张比对后暴露：

| 素材 | 脸部像素被换装覆盖的比例 | 目视复核 |
|---|---|---|
| 111.jpg | 58.5% | 领口压住鼻/嘴 |
| images.jpeg | 58.0% | 同上 |
| images (2).jpeg | 53.2% | 同上 |
| images (1).jpeg | 42.1% | 同上 |
| 123.png | 64.5% | 同上 |
| 3f5c67b03f7f.jpg | 67.1% | 同上 |
| FaceQ1411209084675.png | 81.0% | 同上（卡通负例） |
| images (3).jpeg | 99.4% | 横图负例 |
| images (4).jpeg | 92.1% | 同上 |
| 3652.jpg | 1.9% | **正常**（唯一合格的一张） |
| 91f990d7….jpg | 2.0% | **正常** |

**根因**（据 `[audit] suit_geometry` / `suit_fit_v2` 日志）：
- `suit_geometry.source = estimate` → 本次运行**没有关键点**，
  头长由 `core/face.js` 的 `headMetricsFromBBox` 估算：**头长 = 人像框高 × `HEAD_BBOX_RATIO` 0.30**；
- 该系数假定人像框远高于头（半身/全身构图）。但**证件照构图**下人像框 ≈ 头 + 肩，
  0.30×框高 明显**小于**真实头长 → `chinY` 估高 → 西装领口上移压到鼻/嘴。
  （实测：111.jpg 的 alphaBBox 高 670px → 估头长 201px，而实际头长远大于此。）

**为什么这次会暴露**：开发者工具模拟器不支持人脸检测（`services/faceService.ts` 跳过 `devtools` 平台）
→ 全部走 `estimate` 路径。
**注意**：真机正常时走 `landmarks` 路径不会命中该缺陷；
但**真机上人脸检测失败时同样落到 `estimate` 路径** → 同一缺陷仍可能复现。
建议：把 `HEAD_BBOX_RATIO` 的适用前提（人像框远高于头）显式校验，
或在该路径下对证件照构图改用其它估计（如 `core/suit.js` 的 `estimateHeadByShoulder` 肩线法）。

## 五、需求 → 断言覆盖矩阵（RC-03）

- 需求清单 `工具链/prd_requirements.json` 与RC-01-v1.2的76项对齐；用例协议为 `工具链/coverage_cases.json`，双向校验编号，并强制非空及与RC-01全部编号/描述一致，禁止删项后获得零缺口。
- 每项有输入、实际动作、期望、反例、环境与局限；primary是整条需求主验收，partial仅认领明确的局部能力。
- 文件存在和断言定位检查只证明登记有效。登记的执行状态为NOT_RUN，不能继承历史PASS；当前76项均仍有主验收/证据缺口。
